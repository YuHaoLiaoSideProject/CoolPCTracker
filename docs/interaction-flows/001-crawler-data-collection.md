# Interaction Flow：001-crawler-data-collection（爬蟲資料收集管道）

## 1. 功能概述

**一句話描述**：每日自動抓取原價屋手機版 9 個分類頁，解析出約 1,449 個商品並與既有資料比對，每次成功爬取都累積當日價格點（含價格未變的平價日），輸出供前端展示的最新商品資料。

**核心價值**：以低成本、低風險、可恢復的方式持續累積跨日商品價格歷史，讓後續價格趨勢圖、降價通知、搜尋比價等功能有乾淨且穩定的資料來源。

## 2. 使用者與場景

| 項目 | 內容 |
|------|------|
| **角色** | 系統自動觸發（GitHub Actions 每日排程）；管理者（手動補爬 / 接收異常警報） |
| **觸發入口** | ① 每日 06:00 UTC（台北 14:00）cron 自動觸發 ② 管理者以 workflow_dispatch 手動補爬 |
| **前置條件** | 分類清單（9 個 G 索引）可讀；既有資料檔 `data/items.json` 存在（首次執行則建立）；原價屋手機版可連線 |
| **使用情境** | 每日一次自動執行完整管道：抓頁 → 解碼 → 解析 → 規格解析 → 比對 → 健康檢查 → 存檔；異常時自動重試、跳過失敗分類、必要時發管理員警報且不覆寫既有資料 |

    subgraph 異常與恢復

## 4. 逐步互動說明

### 步驟 1：每日排程觸發爬蟲

| | 描述 |
|---|------|
| **觸發** | GitHub Actions cron 於每日 06:00 UTC（台北 14:00）自動觸發；管理者亦可手動 workflow_dispatch |
| **操作前** | 系統閒置；`data/items.json` 存在上一次爬取資料 |
| **系統回應** | 啟動爬蟲 run，讀取分類清單與 UA 設定，記錄開始時間 |
| **操作後** | 爬蟲 run 已開始，進入抓頁階段 |
| **下一步** | 步驟 2：抓取 9 個分類頁 |

### 步驟 2：抓取 9 個分類頁

| | 描述 |
|---|------|
| **觸發** | fetcher 依序對 `m-list.php?G=1,3,4,5,6,7,8,9,12` 發出 HTTP GET（手機版 UA） |
| **操作前** | 爬蟲 run 已開始，9 個分類頁尚未取得 |
| **系統回應** | 逐頁抓取；單頁失敗自動重試（最多 3 次）；取得頁面原始位元組 |
| **操作後** | 9 個頁面原始內容存在記憶體；失敗頁面依規則跳過或沿用舊資料 |
| **下一步** | 步驟 3：CP950 解碼 |

### 步驟 3：CP950 解碼

| | 描述 |
|---|------|
| **觸發** | 對每個頁面位元組進行 Big5 → UTF-8 解碼 |
| **操作前** | 頁面為 Big5（CP950）編碼位元組 |
| **系統回應** | 以 CP950 解碼（errors='replace'），無法解碼的特殊字元以替代字元呈現、不中斷 |
| **操作後** | 每頁得到可解析的 UTF-8 文字 |
| **下一步** | 步驟 4：解析商品 |

### 步驟 4：解析商品與分類過濾

| | 描述 |
|---|------|
| **觸發** | parser 將 HTML table 結構轉為商品清單 |
| **操作前** | 9 頁 UTF-8 文字已備妥 |
| **系統回應** | `<th>`=子分類標題、`<td>`=商品列；過濾 disabled 加購列與贈品列；G=9 僅保留子分類名稱含「記憶卡」者；解析名稱、價格與標記（Hot！/任搭↓N/↘/尾盤） |
| **操作後** | 約 1,449 個商品（含主/子分類、名稱、價格、標記） |
| **下一步** | 步驟 5：規格解析 |

### 步驟 5：規格解析

| | 描述 |
|---|------|
| **觸發** | spec_parser 依商品分類套用深度或輕量解析 |
| **操作前** | 商品清單已產生 |
| **系統回應** | CPU/GPU/RAM/SSD/HDD/主機板做深度解析（品牌/型號/容量/時脈/腳位等結構化欄位）；記憶卡/套裝/劈發價組合區做輕量解析 |
| **操作後** | 每商品帶有結構化 spec（部分分類可能僅有少量欄位） |
| **下一步** | 步驟 6：產生 ID 並比對 |

### 步驟 6：產生商品 ID 並與既有資料比對

| | 描述 |
|---|------|
| **觸發** | 以 hash(主分類 + 正規化名稱) 產生跨日穩定 ID；與 `data/items.json` 逐商品比對 |
| **操作前** | 解析後商品清單 + 既有 items.json 皆就緒 |
| **系統回應** | 將每商品分類為：新商品 / 價格異動 / 狀態異動 / 未變動 / 今日消失 |
| **操作後** | 產生 diff 結果（待新增、待 append 歷史、待標記 gone、維持原樣） |
| **下一步** | 步驟 7：健康檢查 |

### 步驟 7：健康檢查

| | 描述 |
|---|------|
| **觸發** | 解析完成後檢查商品總數與前次比較 |
| **操作前** | diff 結果已產生 |
| **系統回應** | 若商品數較前次驟降 >20% 或解析出 0 商品 → 判定為異常 |
| **操作後** | 正常 → 進入步驟 8 寫檔；異常 → 不覆寫資料、發管理員 Telegram 警報、直接結束 |
| **下一步** | 步驟 8：更新歷史並寫檔（或結束） |

### 步驟 8：更新歷史並寫檔

| | 描述 |
|---|------|
| **觸發** | store 依 diff 結果更新資料 |
| **操作前** | diff 結果 + 既有 items.json |
| **系統回應** | 每次成功爬取的商品於 history 尾端 append 當日價格點 `[d,p]`（含價格未變的平價日）；更新 status / first_seen / last_seen；失敗分類商品（今日未成功爬取）原樣保留；以原子方式寫出 `data/items.json` 與 `data/meta.json` |
| **操作後** | 兩個資料檔更新完成（git commit 由 CI 後續處理） |
| **下一步** | 步驟 9：回報結果 |

### 步驟 9：回報結果並結束

| | 描述 |
|---|------|
| **觸發** | 寫檔完成後彙整本次 run 結果 |
| **操作前** | 新資料已寫入 |
| **系統回應** | meta.json 記錄 crawled_at、各分類商品數、異動數、失敗分類；輸出執行摘要 log |
| **操作後** | 系統回到閒置狀態，等待明日排程 |
| **下一步** | 無（本次 run 結束） |

## 5. 異常處理

| 錯誤情境 | 系統回饋 | 恢復路徑 |
|------|------|------|
| 單一分類頁連線逾時 / HTTP 非 200 | 自動重試（最多 3 次，間隔退避） | 重試成功則繼續；仍失敗 → 該分類沿用舊資料、meta.json 標記 failed、其餘 8 個分類照常更新 |
| 全部分類頁皆失敗 | run 判定失敗，不覆寫資料 | 管理者收到 Telegram 警報，確認來源後以 workflow_dispatch 手動補爬 |
| 商品數較前次驟降 >20% | 判定疑似改版/解析失效，**不覆寫資料**，發管理員警報 | 人工檢查 parser 並修復；保留既有資料作為對照，修復後補爬 |
| 解析出 0 商品 | 同上述視為異常，保留舊資料 | 檢查 HTML 結構是否改版，更新 parser 後補爬 |
| CP950 解碼遇特殊字元 | errors='replace'，以替代字元呈現，不中斷 | 不需處理；商品仍可解析，fixture 測試涵蓋特殊字元 |
| 商品名稱改動導致 ID 改變 | 商品可能看似「消失 + 新增」 | 以名稱相似度 + 價格連續性做 merge 策略（後續強化）；先保留既有記錄 |
| 排程延遲 / 被跳過 | 資料帶 crawled_at，前端可顯示資料新鮮度 | 管理者以 workflow_dispatch 手動補爬 |
| 寫檔失敗（磁碟滿等） | 原子寫入避免半成品；run 標記失敗 | 既有資料檔不受影響，修正環境問題後重跑 |

## 6. 邊界與限制

| 項目 | 限制 / 行為 |
|------|------|
| 追蹤範圍 | 僅 9 個分類頁約 1,449 商品（全站 6,626 的 22%），非全站爬取 |
| G=9 過濾 | 僅收錄子分類名稱含「記憶卡」的 4 個子分類（Micro SD / SD / CFexpress / MicroSDXC Express）；排除隨身碟、外接硬碟等 |
| 執行頻率 | 每日一次（06:00 UTC）；不支援即時/多頻次抓取 |
| 並發 | 同一時間僅允許一個 run，避免同日重複 append 歷史 |
| 重試與逾時 | 單頁重試 ≤ 3 次；HTTP 逾時需設定上限（建議 10–30 秒） |
| 歷史增長 | 每日一點：每次成功爬取（含平價日）append `[d,p]`，同日重跑冪等不重複；每日約 1,449 點、每點 2 欄位，repo 體積可控 |
| 商品 ID | hash(主分類+正規化名稱)，跨日穩定；名稱正規化（全形/半形、空白）影響 ID 穩定性 |
| 狀態判定 | in_stock / gone 以「商品是否出現在當日清單」判定 |
| 價格缺失 | 價格資訊缺失時不記錄該日價格歷史，商品仍依出現與否判定狀態 |
| 來源禮貌性 | 以手機版 UA 抓取；遵守原價屋使用條款與合理請求頻率 |

## 7. 驗收檢查清單

- [ ] 每日 06:00 UTC cron 能自動觸發爬蟲
- [ ] 依序抓取 9 個分類頁（G=1,3,4,5,6,7,8,9,12）皆成功
- [ ] 頁面以 CP950 正確解碼，特殊字元不中斷解析
- [ ] table 解析出約 1,449 個商品，主/子分類正確
- [ ] disabled 加購列與贈品列被排除，不進入商品清單
- [ ] G=9 僅收錄 4 個「記憶卡」子分類商品，隨身碟/外接碟被排除
- [ ] Hot！/ 任搭↓N / ↘ / 尾盤四種標記正確解析
- [ ] CPU/GPU/RAM/SSD/HDD/主機板為深度規格解析；記憶卡/套裝/劈發價為輕量解析
- [ ] 商品 ID = hash(主分類 + 正規化名稱)，同商品跨日 ID 一致、同日重跑一致
- [ ] 每次成功爬取的商品都 append 當日價格點 `[d,p]`（含平價日）；同日重跑不重複 append
- [ ] 新商品 first_seen 設為當日；今日消失商品標記為 gone
- [ ] 單頁失敗自動重試 ≤ 3 次；仍失敗該分類沿用舊資料並於 meta.json 標記
- [ ] 商品數驟降 >20% 或解析 0 商品 → 不覆寫資料 + 發管理員 Telegram 警報
- [ ] `data/items.json` 與 `data/meta.json` 正確輸出，meta 含 crawled_at / 商品計數 / 健康指標
- [ ] 寫檔失敗時既有資料不受影響（原子寫入）
